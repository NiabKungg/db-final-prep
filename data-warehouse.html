หน้าแรก / Data Warehouse

🏢 Data Warehouse — คลังข้อมูลเพื่อการวิเคราะห์

คะแนน 15 ไม่ออกการออกแบบ — เน้นนิยาม/เปรียบเทียบ/องค์ประกอบ บทอ่านเบา ท่องได้ = ได้คะแนน

1. Data Warehouse คืออะไร

Data Warehouse (คลังข้อมูล) คือ ระบบจัดเก็บข้อมูลเชิงวิเคราะห์ขนาดใหญ่ ที่รวบรวมข้อมูลจากหลากหลายแหล่งทั้งภายในและภายนอกองค์กร นำมาไว้ที่คลังกลาง เพื่อรองรับการตัดสินใจเชิงบริหาร (MIS, DSS, EIS) และงาน Business Intelligence (BI) / Data Science

🔍 เปรียบเทียบให้เห็นภาพ

ฐานข้อมูลประจำวัน (OLTP) เหมือน ร้านค้าหน้าร้าน — ขายของ รับเงิน บันทึกรายการรายวัน เร็ว ๆ ทีละรายการ
Data Warehouse เหมือน ห้องประชุมผู้บริหารที่มีกระดานสรุปทุกอย่าง — รวมยอดขายทุกสาขา ทุกเดือน ย้อนหลัง 5-10 ปี ไว้ให้ดูแนวโน้มและตัดสินใจ ไม่ใช่ให้ใช้ขายของ

2. ลักษณะสำคัญ 4 ประการ (นิยามของ Bill Inmon — ท่องให้ขึ้นใจ!)

Bill Inmon ผู้ถูกยกให้เป็น "บิดาแห่ง Data Warehouse" ให้นิยามลักษณะ 4 ข้อ นี่คือคำตอบมาตรฐานของข้อสอบ:

🎯 Subject-Oriented (เน้นตามหัวเรื่อง)

ไม่จัดเก็บตามกระบวนการทำงานรายวัน แต่จัดตามหัวข้อเชิงธุรกิจที่ผู้บริหารสนใจวิเคราะห์
ตัวอย่าง: แยกเก็บตามยอดขาย (Sales), สินค้า (Product), ลูกค้า (Customer), การตลาด (Marketing)

🧩 Integrated (รวมเป็นหนึ่งเดียว)

ดึงจากหลายระบบที่โครงสร้างต่างกัน แล้วปรับมาตรฐาน + ล้างข้อมูล (Standardization/Cleansing) ให้เป็นรูปแบบเดียวกัน
ตัวอย่าง: สาขา A เก็บเพศ 'M/F', สาขา B เก็บ '1/0', สาขา C เก็บ 'ชาย/หญิง' → ในคลังต้องแปลงเป็นมาตรฐานเดียว

⏳ Time-Variant (ผูกกับแกนเวลา)

ข้อมูลทุกแถวมี Time Dimension/Time Stamp เก็บประวัติย้อนหลังนาน 5–10 ปี รองรับการเทียบแนวโน้มและพยากรณ์
ตัวอย่าง: ดึงรายงานเทียบยอดขายไตรมาส 1 ปีนี้ กับไตรมาส 1 ย้อนหลัง 5 ปี ได้ทันที

🔒 Non-Volatile (เสถียร ไม่แก้ไข)

ข้อมูลที่เข้าคลังแล้วเป็น Read-Only — ผู้ใช้ทั่วไป UPDATE/DELETE ไม่ได้ เพิ่มได้เฉพาะโหลดเป็นรอบ (Batch Load)
ตัวอย่าง: ยอดขายเดือนที่แล้วเข้าคลังแล้ว ห้ามพนักงานแก้ตัวเลขย้อนหลัง เพื่อความถูกต้อง 100%

🧠 วิธีจำ 4 ข้อ

S-I-T-N = "หัวเรื่อง รวมเดียว ผูกเวลา ไม่แก้ไข" (Subject / Integrated / Time-variant / Non-volatile)

3. OLTP vs OLAP / Data Warehouse — ตารางเปรียบเทียบ (ออกบ่อยมาก)

ประเด็นOLTP (Online Transaction Processing)OLAP / Data Warehouse
วัตถุประสงค์งานประจำวัน (จองตั๋ว โอนเงิน ขายของ)วิเคราะห์ + สนับสนุนการตัดสินใจผู้บริหาร (MIS, DSS, EIS)
คำสั่งที่ใช้เน้นเขียน/แก้ (INSERT, UPDATE, DELETE) รายการเล็ก ๆเน้นอ่านปริมาณมาก (SELECT) + นำเข้าแบบ Batch
โครงสร้างER Diagram + Normalization (3NF/BCNF) ลดความซ้ำซ้อนDimensional Model (Star/Snowflake) เน้น query เร็ว
ช่วงเวลาข้อมูลปัจจุบัน/ย้อนหลังสั้น (1–3 ปี)ประวัติยาว 5–10 ปี พร้อมแกนเวลา
ผู้ใช้หลักพนักงานปฏิบัติการ ลูกค้า แอปพลิเคชันผู้บริหาร, Data Analyst, Data Scientist
ปรับแต่งเพื่อเขียน (Write) เร็ว + ข้อมูลซ้ำน้อยอ่านสรุป (Read/Query) เร็ว — ยอมให้มีข้อมูลซ้ำบ้าง

4. สถาปัตยกรรมและองค์ประกอบ

ETL — Extract, Transform, Load (ท่อง 3 คำนี้พร้อมความหมาย)

  1. Extract (สกัดข้อมูล)

    ดึงข้อมูลจากแหล่งต้นทางทุกระบบ — เหมือนเก็บผักจากหลายฟาร์มมารวมกันที่ลาน

  2. Transform (แปลงสภาพ + ทำความสะอาด)

    ตรวจสอบ คัดกรอง ล้าง (Data Cleansing) จัดรูปแบบรหัส คำนวณค่า ให้เป็นมาตรฐานเดียว — เหมือนล้างผัก หั่นผัก คัดของเน่าทิ้ง

  3. Load (นำเข้า)

    โหลดข้อมูลที่สะอาดแล้วเข้าสู่คลังหลักหรือ Data Mart — เหมือนแพ็กใส่กล่องเข้าคลังสินค้าจัดเก็บตามชั้น

🏬 Data Mart คืออะไร

คลังข้อมูลขนาดย่อยที่จัดเฉพาะตามฝ่าย เช่น Data Mart ฝ่ายขาย ฝ่ายการตลาด ฝ่าย HR — เข้าถึงเร็ว เจาะจงงานตัวเอง

📇 Metadata คืออะไร

"ข้อมูลที่อธิบายข้อมูล" — โครงสร้าง นิยาม ที่มาของคอลัมน์/ตาราง เหมือนแผนที่และป้ายชื่อชั้นวางของในคลัง ให้คนหาข้อมูลเจอถูกต้อง

📝 2 แนวคิดการสร้าง Data Mart (ถามเทียบกันได้)

Inmon (Top-Down): สร้าง Enterprise Data Warehouse ศูนย์กลางใหญ่ก่อน แล้วค่อยแตกเป็น Data Marts ย่อย
Kimball (Bottom-Up): สร้าง Data Marts ย่อยรายแผนกก่อน ด้วย Dimensional Model แล้วค่อยรวมเป็นคลังใหญ่

5. Star Schema vs Snowflake Schema (รู้จักไว้ — เขาบอกว่าไม่ออกออกแบบ แต่ถามนิยามได้)

⭐ Fact Table (ตารางข้อเท็จจริง)

อยู่ตรงกลาง เก็บตัวเลขวัดผลทางธุรกิจ (Measures) ที่เกิดจากเหตุการณ์
องค์ประกอบ: FK ไปยังตารางมิติ + ตัวเลข เช่น ยอดขาย (Sales_Amount), จำนวน (Quantity), ส่วนลด, กำไร

🧭 Dimension Table (ตารางมิติ)

ล้อมรอบ Fact Table เก็บบริบท/คำอธิบาย ตอบคำถาม ใคร อะไร ที่ไหน เมื่อไหร่
เช่น Dim_Time (วัน→เดือน→ไตรมาส→ปี), Dim_Customer, Dim_Product, Dim_Store — จัดลำดับชั้น (Hierarchy) เพื่อ Drill-down/Roll-up

6. ประโยชน์และตัวอย่างการใช้งานจริง

🗂️ รวมศูนย์ข้อมูลองค์กร

ผู้บริหาร/ทีมวิเคราะห์เข้าถึงข้อมูลทั้งองค์กรจากแหล่งเดียว รวดเร็ว

📊 ตัดสินใจแบบ Data-Driven

ดูแนวโน้ม ยอดขาย กำไร ผ่าน Dashboard แม่นยำ

⚡ ไม่กระทบระบบหลัก

ดึงไปวิเคราะห์ที่คลัง ระบบขาย/ลงทะเบียน (OLTP) ยังเร็วเหมือนเดิม

🤖 รากฐาน Data Science

ข้อมูลสะอาดพร้อมทำ Data Mining, Machine Learning, พยากรณ์

ตัวอย่างจริงที่อาจารย์ยกในวิดีโอ:

  • ธุรกิจค้าปลีก/ร้านสะดวกซื้อ: วิเคราะห์ยอดขายตามสาขา เทียบวันหยุด vs วันธรรมดา จำแนกกลุ่มสินค้าเพื่อทำโปรโมชัน
  • ภาครัฐ (Government Data Catalog / Open Data): รวบรวมชุดข้อมูลกรม กระทรวง ผ่าน Data Catalog เปิดเผยสถิติให้ประชาชนใช้ร่วมกัน
  • ระบบบริหารน้ำ/ภัยพิบัติ: รวบรวมข้อมูลเซนเซอร์ ปริมาณน้ำฝน มาทำแดชบอร์ดและพยากรณ์ (Forecasting)

📝 แนวข้อสอบ Data Warehouse + ตัวอย่างคำตอบ

📌 หมายเหตุจากโครงข้อสอบ

"ความรู้เบื้องต้นด้าน Data Warehouse ไม่ออกการออกแบบ" — ดังนั้นเตรียมตัวเน้นการบ้าน: นิยาม 4 ข้อ, ตาราง OLTP vs OLAP, องค์ประกอบ/ETL, นิยาม Fact/Dimension และ Star vs Snowflake พอ

ข้อ 1: Data Warehouse คืออะไร และมีลักษณะสำคัญอะไรบ้าง

Data Warehouse คือ ระบบจัดเก็บข้อมูลเชิงวิเคราะห์ขนาดใหญ่ ที่รวบรวมข้อมูลจากหลายแหล่งทั้งภายใน/ภายนอกองค์กร มาไว้คลังกลางเพื่อสนับสนุนการตัดสินใจเชิงบริหารและงาน BI — ลักษณะ 4 ประการตามนิยามของ Bill Inmon: Subject-Oriented (จัดเก็บตามหัวเรื่องเชิงธุรกิจ เช่น ยอดขาย ลูกค้า), Integrated (รวมหลายระบบเป็นมาตรฐานเดียว), Time-Variant (ผูกแกนเวลา เก็บประวัติ 5–10 ปี), Non-Volatile (เข้าคลังแล้วแก้/ลบไม่ได้ อ่านอย่างเดียว)

ข้อ 2: เปรียบเทียบ OLTP กับ Data Warehouse/OLAP

OLTP: รองรับงานประจำวัน เน้นเขียน/แก้ไขรายการเล็ก ออกแบบด้วย ER + Normalization (3NF) เก็บข้อมูลปัจจุบัน ผู้ใช้คือพนักงานปฏิบัติการ/ลูกค้า — ปรับแต่งให้ Write เร็ว
OLAP/DW: รองรับการวิเคราะห์และการตัดสินใจ เน้นอ่านปริมาณมาก ออกแบบด้วย Dimensional Model (Star/Snowflake) เก็บประวัติ 5–10 ปี ผู้ใช้คือผู้บริหาร/นักวิเคราะห์ — ปรับแต่งให้ Read เร็ว ยอมให้ข้อมูลซ้ำบ้าง

ข้อ 3: ETL คืออะไร อธิบายแต่ละขั้นตอน

ETL คือกระบวนการเคลื่อนข้อมูลเข้าคลังข้อมูล 3 ขั้น: Extract — สกัด/ดึงข้อมูลจากแหล่งต้นทางหลากหลายระบบ; Transform — แปลงสภาพ ตรวจสอบ ทำความสะอาด (Cleansing) จัดรูปแบบรหัสให้เป็นมาตรฐานเดียว; Load — นำเข้าข้อมูลที่ผ่านการตรวจแล้วเข้าสู่ Data Warehouse หรือ Data Mart

ข้อ 4: Fact Table กับ Dimension Table ต่างกันอย่างไร และ Star Schema ต่างจาก Snowflake Schema อย่างไร

Fact Table — ตารางกลางเก็บตัวเลขวัดผล (Measures) เช่น ยอดขาย จำนวน ส่วนลด + FK เชื่อมไปยังมิติ
Dimension Table — ตารางล้อมรอบเก็บบริบท/คำอธิบาย (ใคร อะไร ที่ไหน เมื่อไหร่) พร้อมลำดับชั้นสำหรับ Drill-down/Roll-up
Star Schema: Dimension อยู่ชั้นเดียวโดยรอบ Fact — ง่าย เร็ว JOIN น้อย
Snowflake Schema: นำ Dimension ไทำ Normalization แตกเป็นตารางย่อยต่อ — ซ้ำน้อยกว่า แต่ JOIN หลายตาราง Query ช้าลงเล็กน้อย
