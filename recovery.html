🔄 Transaction & Recovery Control — กู้คืนฐานข้อมูลเมื่อระบบล่ม

Transaction Processing รวม 30 คะแนน ข้อสอบ: นิยาม + ACID + เดิน log ทีละบรรทัด บทนี้ออกซ้ำแบบเดิมเกือบทุกปี

1. Transaction คืออะไร

Transaction คือ กลุ่ม/หน่วยของการทำงานเชิงตรรกะ (Logical Unit of Work — LUW) ประกอบด้วยคำสั่ง DML หลายคำสั่ง (SELECT, INSERT, UPDATE, DELETE) ที่ทำงานต่อเนื่องกันเป็นชุดเดียว โดยถือเป็นหน่วยย่อยที่สุดย่อยไม่ได้อีก (Atomic Unit) — ต้องสำเร็จทั้งหมด (All) หรือยกเลิกทั้งหมดเสมือนไม่เคยเกิดขึ้น (Nothing)

ตัวอย่างอื่นที่อาจารย์ยกในวิดีโอ: การยืมหนังสือในห้องสมุด (ตรวจสิทธิ์ → สร้างใบยืมหลัก → เพิ่มรายการหนังสือย่อย → อัปเดตสถานะหนังสือ), การลงทะเบียนเรียน, การจองตั๋วหนังออนไลน์

2. คุณสมบัติ ACID — ออกสอบแทบทุกปี

🅰️ Atomicity (ความเป็นอะตอม)

All or Nothing — สำเร็จทั้งหมดหรือยกเลิกทั้งหมด ถ้าล้มเหลวกลางทางต้อง Rollback เสมือนไม่เคยเกิด
ตัวอย่าง: ยืมหนังสือ 4 เล่ม บันทึกสำเร็จ 3 เล่มแล้วระบบขัดข้องในเล่มที่ 4 → ต้องยกเลิกรายการยืมทั้ง 4 เล่ม

🅲 Consistency (ความคงเส้นคงวา)

Transaction ต้องพาฐานข้อมูลจากสถานะถูกต้อง → สู่สถานะถูกต้องอีกสถานะ โดยไม่ละเมากฎ Integrity (PK, FK, Check)
ตัวอย่าง: เงินรวมในระบบธนาคารก่อนและหลังโอนต้องเท่าเดิมเสมอ (A ลด 1,000, B เพิ่ม 1,000 → รวมเท่าเดิม)

🅸 Isolation (ความโดดเดี่ยว)

หลาย Transaction ทำพร้อมกัน ผลลัพธ์ต้องเสมือนทำทีละตัวตามลำดับ — ไม่เห็นข้อมูลกลางคันของกันและกัน
ตัวอย่าง: ระหว่างที่ A กำลังโอนเงิน (ยังไม่ Commit) คนอื่นที่เปิดดูยอดของ A ต้องยังเห็นยอดเดิม

🅳 Durability (ความคงทน)

เมื่อ Commit แล้ว การเปลี่ยนแปลงต้องถูกเก็บถาวรลงดิสก์ — ไฟดับ เครื่องล่ม ก็ไม่หาย
ตัวอย่าง: กดโอนเงินแล้วระบบขึ้น "สำเร็จ" ต่อให้ไฟดับพรุ่งนี้ รายการก็ต้องอยู่ครบ

🧠 วิธีจำ ACID แบบเรื่องเดียวจบ

"โอนเงินต้อง Aครบทุกขั้น (All or Nothing) เงินรวมต้อง Cเท่าเดิม ระหว่างโอนต้อง Iโดดเดี่ยวไม่ให้คนอื่นแอบเห็น กดสำเร็จแล้วต้อง Dอยู่ยาวแม้ไฟดับ"

สถานะของ Transaction

3. Recovery Control คืออะไร ทำไมจึงต้องมี

Recovery Control คือ กลไกและกระบวนการของ DBMS ในการคืนสภาพ (Restore/Recover) ฐานข้อมูลให้กลับสู่สถานะถูกต้องสมบูรณ์ (Consistent State) เมื่อเกิดความล้มเหลว เช่น System Failure, ไฟดับ, Transaction ล่มกลางทาง

🛡️ รักษา A + D

การันตี Atomicity (UNDO ตัวที่ไม่เสร็จ) และ Durability (REDO ตัวที่ Commit แล้วไม่ให้หาย)

🚫 ป้องกันข้อมูลพัง

ไฟดับระหว่างเขียนข้อมูล ทำให้ข้อมูลในดิสก์ค้างครึ่ง ๆ กลาง ๆ → Recovery ทำให้กลับสู่สถานะถูกต้อง

↩️ รองรับการยกเลิก

โปรแกรมเมอร์สั่ง ROLLBACK กลางคัน หรือสื่อจัดเก็บเสียหาย ก็กู้คืนได้

🔍 เปรียบเทียบให้เห็นภาพ

Recovery เหมือน ระบบเซฟเกม + CCTV ในเกม: ทุกการกระทำถูกบันทึกลง "สมุดบันทึก" (Log File) ก่อนทำจริงเสมอ เมื่อเกมค้าง/ดับ ก็เปิดสมุดย้อนดูว่าใครทำอะไรค้างอยู่ — ที่ไม่เสร็จก็ย้อนลบ (UNDO) ที่เสร็จแล้วแต่ยังไม่ได้เขียนลงสนามจริงก็ทำซ้ำให้ครบ (REDO)

4. Log File — หัวใจของการ Recovery

Log File (System Log / Journal) คือ ไฟล์บันทึกประวัติการเปลี่ยนแปลงของทุก Transaction ลง Hard Disk แต่ละรายการ (Log Record) ประกอบด้วย:

องค์ประกอบความหมาย
Transaction IDว่า log นี้เป็นของ Transaction ไหน (T1, T2, ...)
Operation TypeSTART, WRITE/UPDATE, COMMIT, ABORT
Data Itemแก้ข้อมูลช่องไหน (เช่น A, B, C)
Before Image (Old Value)ค่าก่อนแก้ไข → ใช้ทำ UNDO (ย้อนคืน)
After Image (New Value)ค่าหลังแก้ไข → ใช้ทำ REDO (ทำซ้ำ)

⚠️ กฎเหล็ก: Write-Ahead Logging (WAL)

ต้องเขียน Log ลง Hard Disk ก่อนเขียนข้อมูลจริงเสมอ — เพราะถ้าข้อมูลจริงเปลี่ยนไปแต่ Log ยังไม่มี เราจะไม่มีทางรู้เลยว่าต้องย้อน/ทำซ้ำอะไร ทำให้กู้คืนไม่ได้

5. Log-based Recovery 2 รูปแบบ

ประเด็นDeferred Update (No-UNDO/REDO)Immediate Update (UNDO/REDO)
การเขียนลง Diskเลื่อนการเขียนข้อมูลจริงออกไป — เขียนจริงเมื่อ Commit แล้วเท่านั้นเขียนข้อมูลจริงลง Disk ได้ทันทีระหว่างทำงาน (ก่อน Commit)
UNDOไม่ต้อง (No-UNDO) — ข้อมูลจริงยังไม่ถูกแตะถ้ายังไม่ Commitต้อง UNDO — ถ้าล่มตอนยังไม่ Commit ต้องเอา Before Image คืนค่า
REDOต้อง REDO — Transaction ที่ Commit แล้วแต่ข้อมูลอาจค้างใน Bufferต้อง REDO — ยืนยันความคงทนของตัวที่ Commit แล้ว

🧠 วิธีจำ

Deferred = เลื่อนเขียน → ไม่เคยเขียนก่อน Commit → ไม่มีอะไรให้ย้อน (No-UNDO)
Immediate = เขียนทันที → อาจเขียนไปแล้วทั้งที่ยังไม่ Commit → ต้องเตรียมย้อน (UNDO)

6. ขั้นตอน Recovery เมื่อระบบ Crash (เดินตามสไลด์อาจารย์)

  1. สแกน Log — จัดแบ่ง Transaction เป็น 2 กลุ่ม

    ดูว่า Transaction ไหนมี <COMMIT> ใน Log:

    • Redo-List = มี START และมี COMMIT → ทำสำเร็จแล้ว ต้องทำซ้ำให้แน่ใจ (REDO)
    • Undo-List = มี START แต่ไม่มี COMMIT → ค้างกลางทาง ต้องย้อน (UNDO)
  2. UNDO Phase — สแกนย้อนจากล่างขึ้นบน (Backward)

    สำหรับ Transaction ใน Undo-List: เอา Before Image (ค่าเก่า) เขียนกลับทีละรายการ จากนั้นบันทึก <ABORT T> ลง Log

  3. REDO Phase — สแกนไปข้างหน้าจากบนลงล่าง (Forward)

    สำหรับ Transaction ใน Redo-List: เอา After Image (ค่าใหม่) เขียนซ้ำลงฐานข้อมูล เพื่อการันตี Durability

  4. ผลลัพธ์ — ฐานข้อมูลกลับสู่ Consistent State 100%

    ตัวเสร็จแล้วยังอยู่ครบ (Durability) ตัวค้างถูกลบเสมือนไม่เคยเกิด (Atomicity)

📌 โจทย์ตัวอย่างที่ออกสอบ: Recovery จาก Log (Immediate Update)

ระบบ Crash ณ จุดที่ระบุ — จงหาค่าของ A, B, C หลัง Recovery

Log Recordความหมาย
<START T1>T1 เริ่มทำงาน
<WRITE T1, A, 100, 200>T1 เขียน A: ค่าเก่า 100 → ค่าใหม่ 200
<START T2>T2 เริ่มทำงาน
<WRITE T2, B, 50, 80>T2 เขียน B: ค่าเก่า 50 → ค่าใหม่ 80
<COMMIT T1>T1 ยืนยันสำเร็จ
<START T3>T3 เริ่มทำงาน
<WRITE T3, C, 30, 90>T3 เขียน C: ค่าเก่า 30 → ค่าใหม่ 90
💥 SYSTEM CRASHระบบล่ม ณ จุดนี้
เฉลยทีละขั้น (ตามสูตร Recovery)

ขั้นที่ 1 — สแกนจัดกลุ่ม:

  • T1: มี START + มี COMMIT → Redo-List = {T1}
  • T2: มี START ไม่มี COMMIT → Undo-List = {T2}
  • T3: มี START ไม่มี COMMIT → Undo-List = {T2, T3}

ขั้นที่ 2 — UNDO (ย้อนจากล่างขึ้นบน):

  • T3: คืนค่า C = 30 (Before Image)
  • T2: คืนค่า B = 50 (Before Image)
  • บันทึก <ABORT T3>, <ABORT T2> ลง Log

ขั้นที่ 3 — REDO (ไปหน้าจากบนลงล่าง):

  • T1: เขียน A = 200 (After Image) ซ้ำลงฐานข้อมูล

คำตอบ: A = 200, B = 50, C = 30 — ฐานข้อมูลกลับสู่สถานะถูกต้อง 100% ✅

7. SAVEPOINT / ROLLBACK — โจทย์ SQL ที่ชอบออกประกอบ

สมมติตาราง Employee เดิมมีพนักงาน 4 คน ลำดับคำสั่งดังนี้:

DELETE FROM Employee;                          -- ลบทั้งหมด เหลือ 0 คน
INSERT INTO Employee VALUES ('E05','Somchai'); -- 1 คน
SAVEPOINT P1;                                  -- ตั้งจุดเซฟ P1
INSERT INTO Employee VALUES ('E06','Somsri');  -- 2 คน
SAVEPOINT P2;                                  -- ตั้งจุดเซฟ P2
INSERT INTO Employee VALUES ('E07','Somsak');  -- 3 คน
ROLLBACK TO P1;                                -- ถอยกลับไปจุด P1
  1. ROLLBACK TO P1 ยกเลิกเฉพาะ "หลัง P1"

    ยกเลิก INSERT ของ E06 และ E07 → เหลือพนักงานเพียง E05 (1 แถว)

  2. ถ้าต่อจากนั้นสั่ง ROLLBACK เฉย ๆ (ไม่ระบุ savepoint)

    ถอยทั้งหมดไปจุด Commit ล่าสุด → การ DELETE 4 คนแรกถูกยกเลิกด้วย → กลับมาได้ พนักงาน 4 คนเดิม

  3. ข้อควรระวังที่ข้อสอบชอบหลอก

    ถ้าแทรกคำสั่ง DDL (CREATE/TRUNCATE/DROP) เข้ามากลางคัน → DDL จะ Auto-Commit ทันที → สั่ง Rollback คำสั่ง DML ก่อนหน้าไม่ได้อีกเลย!

📝 แนวข้อสอบ Recovery + ตัวอย่างคำตอบ

ข้อ 1: Transaction คืออะไร พร้อมตัวอย่าง

Transaction คือ กลุ่มคำสั่ง DML หลายคำสั่งที่ทำงานต่อเนื่องกันเป็นหน่วยงานเชิงตรรกะเดียว (LUW) ซึ่งย่อยไม่ได้อีก และต้องสำเร็จทั้งหมดหรือยกเลิกทั้งหมด (All or Nothing) — ตัวอย่าง: การโอนเงินระหว่างบัญชี A → B ประกอบด้วยการหักเงิน A และเพิ่มเงิน B ซึ่งต้องเกิดคู่กันเสมอ หากหัก A แล้วระบบล่มก่อนเพิ่ม B ต้อง Rollback คืนเงินให้ A

ข้อ 2: Recovery Control คืออะไร และรักษาคุณสมบัติ ACID ตัวใด

Recovery Control คือ กลไกของ DBMS ในการคืนสภาพฐานข้อมูลกลับสู่ Consistent State เมื่อเกิดความล้มเหลว (ไฟดับ ระบบล่ม) โดยอาศัย Log File — รักษา 2 คุณสมบัติคือ Atomicity (Transaction ค้างถูก UNDO เสมือนไม่เคยเกิด) และ Durability (Transaction ที่ Commit แล้วถูก REDO ให้คงอยู่ถาวร)

ข้อ 3: อธิบายคุณสมบัติ ACID พร้อมยกตัวอย่างทีละตัว

Atomicity: All or Nothing — ยืมหนังสือ 4 เล่ม พลาดเล่มที่ 4 → ยกเลิกทั้ง 4
Consistency: จากถูกต้องไปสู่ถูกต้อง ไม่ละเมากฎ PK/FK — ยอดเงินรวมก่อน-หลังโอนเท่าเดิม
Isolation: ทำพร้อมกันเสมือนทีละตัว — คนอื่นไม่เห็นยอดกลางคันของการโอน
Durability: Commit แล้วถาวร — สลิปโอนสำเร็จไม่หายแม้ไฟดับ

ข้อ 4 (โจทย์เดิน log): Log มี START T1 → WRITE(T1,A,10,20) → START T2 → WRITE(T2,B,5,8) → COMMIT T1 → CRASH — จงหาค่า A, B หลัง Recovery

Redo-List = {T1} (มี COMMIT), Undo-List = {T2} (ไม่มี COMMIT)
UNDO: คืน B = 5 (ค่าเก่า) เขียน ABORT T2
REDO: เขียน A = 20 (ค่าใหม่) ซ้ำ
คำตอบ: A = 20, B = 5

🎬 ลองทำแบบทดสอบด่วน

Q1Before Image (ค่าเก่า) ใน Log File ใช้ทำอะไร?

เฉลย ข้อ 3 — Before Image = ค่าก่อนแก้ ใช้สำหรับ UNDO (ย้อนคืน) ส่วน After Image (ค่าใหม่) ใช้สำหรับ REDO

Q2ตามกฎ Write-Ahead Logging (WAL) ต้องเขียนอะไรก่อน?

เฉลย ข้อ 1 — Log ต้องมาก่อนข้อมูลจริงเสมอ ไม่งั้นเมื่อระบบล่มจะไม่มีข้อมูลพอให้กู้คืน

Q3Transaction ใดต้องถูกทำ UNDO เมื่อระบบ Crash?

เฉลย ข้อ 4 — มี START แต่ไม่มี COMMIT = ค้างกลางทางตอนล่ม ต้อง UNDO เสมือนไม่เคยเกิด (ส่วนที่มี COMMIT แล้วให้ทำ REDO แทน)
